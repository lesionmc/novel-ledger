# 06 · 技术方案

本文档为项目复盘补写，技术事实以代码为准（依据：`scripts/*.py`、`web/server.py`、`web/static/*`、`start-web.bat`、`.gitignore`、`.env.example`）。

## 一、选型结论（ADR 简化版）

### ADR-1 · 运行时与依赖：选「纯 Python 标准库、零第三方」

| 项 | 内容 |
|---|---|
| **决策** | 只用 Python 标准库（`argparse/json/os/re/sys/time/urllib/subprocess/http.server/collections`），`requirements.txt` 不存在 |
| **备选 A（选中）** | 纯标准库 + `urllib.request` 直发 OpenAI 兼容协议 |
| **备选 B** | Flask / FastAPI + `requests` + `openai` SDK |
| **备选 C** | LangChain / LlamaIndex 等编排框架 |
| **选 A 的理由** | ① 目标用户是写作者，`pip install` 是最大流失点；② 依赖越少，两年后越不会「跑不起来」；③ OpenAI 兼容协议本身就是一个 `POST /chat/completions`，SDK 带来的便利 < 它带来的版本地狱 |
| **放弃 B/C 的原因** | B 引入 3+ 传递依赖与安装失败风险；C 的记忆/检索抽象与本项目「结构化账本」思路冲突，且重度依赖向量库（违反离线可用） |
| **代价** | 无连接池、无自动重试库、无异步；HTTP 与 SSE 全部手写 |
| **何时需重新评估** | 需要多用户并发（>5 人同时写章）、需要 WebSocket 双向推送、或需要接入非 OpenAI 兼容协议（如 Anthropic 原生）时 |

### ADR-2 · 长篇记忆机制：选「结构化滚动状态账本」

| 项 | 内容 |
|---|---|
| **决策** | 一本书一份 `story_state.md`，固定 7 小节，每章后由模型读「旧账 + 本章正文」**整体覆盖重写** |
| **备选 A（选中）** | 结构化滚动账本（覆盖式重写） |
| **备选 B** | 每章文末追加摘要、截尾保留最近 N 章摘要 |
| **备选 C** | 全量前文塞上下文（长上下文硬扛） |
| **选 A 的理由** | ① 上下文恒定，写第 50 章与第 2 章成本一致；② 账本是 Markdown，作者能直接手改、能 diff、能回滚；③ 可把「计数核对 / 伏笔状态 / 物件防漂移」写成**规则**交给模型执行 |
| **放弃 B 的原因** | 实测截尾记忆会**穿帮**：早期每章只留 400 字摘要，第 2 章就编出「潜入办公室」这种没发生过的情节（`books/雾城档案/chapters/_bak_v1_截尾记忆/` 是当时的现场） |
| **放弃 C 的原因** | 成本随章数平方增长；且注意力稀释，事实反而更容易错 |
| **代价** | 账本正确性 100% 依赖模型输出质量；模型输出被截断就会**损坏账本**（这正是当前示例书的实际状态，见风险 R-09） |
| **何时需重新评估** | 单书超过 ~60 章、账本单节过长导致输入逼近 5k token 阈值时；或换用的模型不遵守「整体覆盖重写」指令时 |

### ADR-3 · Web 后端：选「标准库 ThreadingHTTPServer + 自写 JSON 路由」

| 项 | 内容 |
|---|---|
| **决策** | `http.server.ThreadingHTTPServer` + 手写 `do_GET/do_POST/do_PUT` 三段路由 + `subprocess` 调引擎脚本 |
| **备选 A（选中）** | 标准库 HTTP 服务 + 路径分段路由（`segs[0] == "api"` 起手） |
| **备选 B** | Flask |
| **备选 C** | FastAPI + Uvicorn |
| **选 A 的理由** | 与 ADR-1 一致：零安装；引擎本来就是命令行脚本，Web 只需「起子进程 + 收 stdout/stderr」，没有需要框架解决的复杂度 |
| **放弃 B/C 的原因** | 引入依赖，与项目第一性原则冲突 |
| **代价** | 路由是手写 if 链，**没有框架帮你校验方法/路径**，缩进错一格就会把一段路由整段吞进别的函数体（见 §五 难点 6） |
| **何时需重新评估** | 路由超过 ~25 条、需要鉴权中间件、需要 OpenAPI 文档自动生成时 |

### ADR-4 · 去 AI 味策略：选「L1 词表本地筛 + L2 模型精判 + 人工确认后 apply」

| 项 | 内容 |
|---|---|
| **决策** | 两级检测 + 一次受控写入；只自动应用 hard 级；apply 前自动备份 |
| **备选 A（选中）** | L1 词表/正则（零 token）+ L2 模型精判（只喂命中句）+ apply（只改 hard） |
| **备选 B** | 纯词表正则替换（不调模型） |
| **备选 C** | 整章交给模型「帮我润色」（不检测，直接改写全文） |
| **选 A 的理由** | 词表提供**可解释、可复现、零成本**的体检；模型解决词表「语境依赖」的误判（如「不是X而是Y」在推理句是正常表达）；apply 只改 hard 保证「机器不替作者做文风决定」 |
| **放弃 B 的原因** | 中文语境依赖强，纯规则误伤率不可接受 |
| **放弃 C 的原因** | 整章改写会连人设、情节、句式一起改掉，且不可回溯；还常引入新套话 |
| **代价** | 三步操作，用户学习成本高于「一键润色」 |
| **何时需重新评估** | 词表维护成本超过收益（如命中率长期 <5%）、或出现能可靠保留风格的改写模型时 |

### ADR-5 · 测试：选「零网络零依赖自写断言脚本」

| 项 | 内容 |
|---|---|
| **决策** | `scripts/smoke_test.py`：23 条断言，`sys.exit(1)` 表示失败，可接 CI；网络调用全部用 monkeypatch 桩函数替掉 |
| **备选 A（选中）** | 标准库自写 `check()` 断言 + 临时目录 + monkeypatch |
| **备选 B** | pytest + responses/vcr 录制回放 |
| **选 A 的理由** | 与 ADR-1 一致；且「跑测试」这一动作对作者来说必须和「写章」一样零门槛 |
| **放弃 B 的原因** | 需要装 pytest，且 mock HTTP 库本身又是一层依赖 |
| **代价** | 无测试发现/参数化/覆盖率统计，靠人工加断言 |
| **何时需重新评估** | 断言数超过 ~60 条、需要覆盖率门禁、或需要并行执行时 |

## 三、技术栈清单

| 层 | 技术 | 版本/说明 | 是否第三方 |
|---|---|---|---|
| 语言 | Python | 3.9+ 语法（README 标注）；`start-web.bat` 实际指向 3.13.12；`web/server.py` 用到 `ThreadingHTTPServer`（3.7+） | 否 |
| CLI | `argparse` | 两个引擎各自一套参数 | 否 |
| HTTP 客户端 | `urllib.request` | 手写 `POST /chat/completions`；`write_chapter.py` 默认 timeout 240s，`deai.py` 180s | 否 |
| HTTP 服务端 | `http.server.ThreadingHTTPServer` + `BaseHTTPRequestHandler` | 绑定 `127.0.0.1`，端口由 `--port` 指定（模块默认 8000，`start-web.bat` 传 8801） | 否 |
| 子进程 | `subprocess.run` | `cwd=ROOT`、`encoding="utf-8"`、`errors="replace"`；超时按动作分级 | 否 |
| 前端 | 原生 HTML/CSS/JS | **无框架、无构建、无 npm**：`index.html` + `style.css` + `app.js` | 否 |
| 流式 | SSE（`text/event-stream`） | 后端手写 `event: delta/done/error`；前端 `fetch` + `ReadableStream` 逐块解析 | 否 |
| 配置 | 自写极简 `.env` 解析 | `key=value`，`#` 注释，去首尾引号；不识别多行/变量插值 | 否 |
| 测试 | 自写 `check()` 断言 | 零网络（monkeypatch `_post_chat` / `urlopen`） | 否 |
| 持久化 | 纯文件（Markdown + JSON） | 无数据库、无 ORM | 否 |
| 版本 | git | 仓库 `github.com/lesionmc/novel-ledger`，MIT | — |

> **第三方依赖数量：0**。这是本项目最硬的架构约束，任何新增依赖都应先回到 ADR-1 走一遍评估。

## 四、部署架构

### 4.1 形态：本地单机、单用户

```
┌──────────────── 一台 Windows 开发机 ────────────────┐
│                                                      │
│  start-web.bat                                       │
│   ① chcp 65001                 （切 UTF-8 代码页）    │
│   ② cd /d "%~dp0.."            （切到项目根）         │
│   ③ python web\server.py --port 8801                 │
│                                                      │
│  ┌───────────────┐        ┌────────────────────────┐ │
│  │ 浏览器        │◀──────▶│ server.py (127.0.0.1)  │ │
│  │ 127.0.0.1:8801│  HTTP  │  └ subprocess → 引擎脚本│ │
│  └───────────────┘        └───────────┬────────────┘ │
│                                       │ 出站 HTTPS    │
│  ┌───────────────┐                    ▼              │
│  │ 终端（可选）  │            ┌──────────────────┐   │
│  │ python scripts│            │ 模型厂商 API     │   │
│  │  /xxx.py      │            └──────────────────┘   │
│  └───────────────┘                                   │
│  项目文件：books/ scripts/ web/ .env 全在本地磁盘     │
└──────────────────────────────────────────────────────┘
```

| 部署项 | 结论 |
|---|---|
| 运行形态 | 本地进程，随开随关；无 systemd / 无 Docker / 无反向代理 |
| 监听地址 | `127.0.0.1`（硬编码，不对外网开放） |
| 端口 | `server.py` 模块默认 `8000`；`start-web.bat` 实际传 `--port 8801` |
| 启动入口 | Windows：`start-web.bat`（内含绝对路径 python，见 §七 运维 R-11）；macOS/Linux：`python3 web/server.py --port 8801` |
| 并发 | `ThreadingHTTPServer` 多线程，但**引擎子进程无任何并发保护**；同一本书同时点两次「写章」会互相覆盖（风险 R-07） |
| 数据位置 | 全部在项目目录下，卸载 = 删目录；`books/*/chapters/` 被 `.gitignore` 排除，**不入版本库** |
| 水平扩展 | 不支持，也不打算支持（单作者单人使用） |

### 4.2 三种使用形态对照

| 形态 | 命令 | 适合 |
|---|---|---|
| 纯 CLI | `python scripts/write_chapter.py --book books/xxx --chapter N` | 批量/脚本化/服务器无浏览器 |
| Web 工作台 | `start-web.bat` → 浏览器 | 日常写作、审稿、改账本 |
| 测试 | `python scripts/smoke_test.py` | 改代码后回归，零网络 |

## 五、关键难点与对策（真实踩过）

> 前 5 条是本项目立项阶段就在 README 记录的坑；后 4 条是本轮补写文档时**新核对出来的**。每条都给出「现象 → 根因 → 解法 → 证据」。

### 难点 1 · 推理模型 reasoning 失控，吞光 max_tokens

| 项 | 内容 |
|---|---|
| **现象** | `agnes-2.5-flash` 在长上下文 + 长创作指令下，返回空正文，`finish_reason=length` |
| **根因** | 模型的思考（reasoning）token 与输出 token 共用 `max_tokens` 预算，思考把预算吃光 |
| **解法** | 请求体固定带 `"reasoning_effort": "low"`（`reasoning_effort != "none"` 时才带，不支持的网关会忽略）；`max_tokens` 提到 12000 |
| **证据** | `write_chapter.py:249` `if reasoning_effort and reasoning_effort != "none": payload["reasoning_effort"] = …`；`call_llm` 默认 `max_tokens=12000`；实测思考 12000 → 419 tokens |
| **现状** | 已闭环，所有 `call_llm` 调用点（写章/账本/审计/L2/初始化/Web 对话）均已带该参数 |

### 难点 2 · 输入超 ~5k tokens 又触发上一条失控

| 项 | 内容 |
|---|---|
| **现象** | 更新账本时把整章 5500 字正文塞进 prompt → 请求失败/返回空 |
| **根因** | 输入规模本身会放大 reasoning 失控概率（不是输出预算问题） |
| **解法** | ① 账本更新与审计对正文做**首尾截短**（>3200 字 → 前 1400 + 省略提示 + 后 1400）；② 审计额外把账本的「## 伏笔账本」整节正则剥掉；③ L2 精判**只喂命中句 + 该行原文**，从不喂全文 |
| **证据** | `update_state()` 注释「ch4 实测修复」；`audit_chapter()` 注释「输入瘦身」；`build_l2_prompt()` 注释「不喂全文，防推理失控」 |
| **现状** | 已闭环；代价是正文中段事实可能漏入账（prompt 里已显式提示模型「如中间有必须入账的事实请结合旧账推断标注」） |

### 难点 3 · 低版本模型不守边界

| 项 | 内容 |
|---|---|
| **现象** | `agnes-2.0-flash` 一口气写 1.7 万字、跨多章内容、称呼串戏（把前妻叫「老陈」） |
| **根因** | 低版本模型对「只写一章 / 遵循角色称呼规则」的指令服从度不足 |
| **解法** | 主力固定 `agnes-2.5-flash` + `reasoning_effort=low`；把称呼规则写进 `设定.md` 硬性约束（第 4 条：陈默被叫「陈法医/陈默」，宋茵叫「老陈」，前妻叫「陈默」）；靠审计流程发现串戏 |
| **证据** | `sample_book/设定.md`「硬性写作约束」第 4 条；`build_context()` 明确要求「人物名字/身份/称呼与角色卡一致」 |
| **现状** | 已缓解（换模型 + 设定写死）；**未消除**——换任何新模型都要重跑一遍前 3 章验证 |

### 难点 4 · 截尾记忆穿帮

| 项 | 内容 |
|---|---|
| **现象** | 早期方案每章只留 400 字摘要，模型「凭空编造上一章没发生的事」（第 2 章编出「潜入办公室」） |
| **根因** | 摘要不可避免地丢事实，模型面对空缺会**补脑**而非承认不知道 |
| **解法** | 改成结构化滚动账本（ADR-2）：7 小节固定结构 + 覆盖式重写 + 规则 9 强制「冲突必须显式标注而不许悄悄覆盖」 |
| **证据** | `books/雾城档案/chapters/_bak_v1_截尾记忆/` 保留了当时的版本；`STATE_UPDATER_PROMPT` 规则 9 |
| **现状** | 已根治 |

### 难点 5 · 道具漂移

| 项 | 内容 |
|---|---|
| **现象** | 设定没写死外观，徽章跨版本从「荆棘眼」漂成「鸟形袖扣」 |
| **根因** | 模型每次重新生成外观描述，没有不可变事实源 |
| **解法** | ① `设定.md` 必须把关键道具外观写死（模板已含示例：银鸟徽章·银色·鸟形·翅膀收拢）；② 账本「## 关键物件」小节规则：**外观一经写死严禁改动**；③ 审计把「物件归属/外观与账本冲突」列为第一类检查项 |
| **证据** | `STATE_TEMPLATE`「关键物件（外观一经写死严禁漂移）」；`STATE_UPDATER_PROMPT` 规则 7；`AUDIT_PROMPT` 第 1 条 |
| **现状** | 已缓解；审计是最后一道闸，但依赖模型自觉比对 |

### 难点 6 · 手写路由被缩进吞掉（本轮新核对）🔴

| 项 | 内容 |
|---|---|
| **现象** | `web/server.py` 中 `POST /api/books`、`POST /api/book/from-chat`、`POST /api/book/{book}/write|audit|scan|polish|apply` 这些路由代码，实际位于 `_chat_stream()` 方法体内，不在 `handle_api_post()` 里 |
| **根因** | SSE 流式功能（v3）插入时，`if segs == ["books"]:` 及后续代码缩进是 8 空格（方法体层级），而非 `handle_api_post` 应有的 8 空格——两段代码缩进相同，但中间没有 `return` 隔断，导致后半段落进了前一段的函数体 |
| **证据（AST 实测）** | `handle_api_post` → 行 378–414；`_chat_stream` → 行 416–**575**。即 477–575 行（books/from-chat/write/audit/scan/polish/apply）属于 `_chat_stream` |
| **影响** | ① 这些 POST 路由不可达，调用会落到 `handle_api_post` 末尾的 `api_error(404, "no route")`；② 即便真被调用，`segs` 在 `_chat_stream` 作用域内未定义 → `NameError` → 500 |
| **解法（待修）** | 把 477–575 行整体**上移**到 `handle_api_post` 方法体内（`_chat_stream` 定义之前），恢复 `def _chat_stream` 之前的 `return` 链 |
| **验收方式** | 修完后用 `python -c "import ast; …"` 复核方法边界；再逐条 `curl -X POST /api/books` 等验证 |

### 难点 7 · 文本替换锚会吞引号 / AI 改 AI 引入新套话

| 项 | 内容 |
|---|---|
| **现象** | ① 对话句以引号开头时，自动切句把前引号包进去、改写版没有 → 替换后丢引号、格式破损；② 改写把「某种说不清的金属味」换成「若有若无的铁锈气」，而后者也在词表里 → 旧腔去、新腔来 |
| **根因** | ① 句子边界字符集不含引号；② 模型不知道词表全貌 |
| **解法** | ① `SENT_END` 把 `"'“”‘’「」『』` 全部算作句子边界（`extract_full_sentence()`），锚点只切到引号**内侧**；② apply 后强制 re-scan 复查，并把该规则写进流程（见 `05-业务流程.md` §2.3） |
| **证据** | `SENT_END = "。！？；…\"'“”‘’「」『』"`；冒烟测试「引号不算句内容(不吞引号)」「对话句替换且引号保留」两条断言 |
| **现状** | ① 已闭环并有回归断言；② 靠流程约束（无自动检测） |

### 难点 8 · 前端无构建，JS/HTML 字符串错误只有运行时才暴露（本轮新核对）🟡

| 项 | 内容 |
|---|---|
| **现象** | `app.js` 里设置面板的 HTML 是由模板字符串拼出来的，存在多处破损标记：`<input<type="password"`（357–364 行各 input）、内联 `<style>` 文本被写成 `{form-section h {4 {…}`（366 行）、`<textarea id="fileEdit"></textarea">`（435 行）、`onclick="…"()`（443/444 行） |
| **根因** | 这些 HTML 藏在 JS 模板字符串里，`node --check` 只校验 JS 语法（**实测 app.js 语法检查通过**），浏览器解析时才出问题 |
| **影响** | 设置面板的输入框可能渲染异常（type 失效、样式片段被当文本显示）；建书向导的按钮/文本框可能错位 |
| **解法（待修）** | 逐个修正破损标记，并在浏览器实际点开 ⚙ 设置 / 建书向导做一次冒烟 |
| **验收方式** | 打开设置面板 → 6 个输入框全部可见且 `type` 生效 → 保存后 `.env` 对应行被改写 |

### 难点 9 · `renderBrief()` 调用了不存在的函数（本轮新核对）🟡

| 项 | 内容 |
|---|---|
| **现象** | `app.js:538` 写作 `$const("#bookNameInput").value = …`，`$const` 未定义 |
| **根因** | 手误（应为 `$("#bookNameInput")`）；`$` 是合法标识符字符，`$const(...)` 在语法上是一个普通函数调用，所以 `node --check` 不报错 |
| **影响** | 建书向导点击「💡 让 AI 提取书名/卖点」后，`renderBrief()` 在渲染完摘要卡之后抛 `ReferenceError`，后续「书名输入框回填」不执行 |
| **解法（待修）** | 改为 `$("#bookNameInput").value = state.chat.name \|\| "";` |
| **验收方式** | 建书向导 → 提取书名 → 书名输入框被自动回填 |

## 六、非功能设计

### 6.1 性能

| 场景 | 实测/配置 | 说明 |
|---|---|---|
| 写 1 章（约 3000 字） | 约 1–3 分钟 | 两次模型调用（正文 + 账本）；前端 `busy("模型写作中（约 1-3 分钟…）")` |
| 全书体检 `--scan` | 秒级、零 token | 纯本地正则/计数；Web 侧子进程 timeout 120s |
| 单章精判 `--polish` | 十秒级 | Web 侧 timeout 300s |
| 应用改写 `--apply` | 亚秒级 | 纯本地文本替换；Web 侧 timeout 60s |
| 一致性审计 | 约 1 分钟 | 一次模型调用；走通用 timeout 900s |
| 引擎子进程超时 | 通用 900s；scan 120s / polish 300s / apply 60s | `run_engine()` 超时返回 `(False, "", "引擎执行超时")` |
| HTTP 超时 | `write_chapter` 240s；`deai` 180s；Web `llm_chat` 240s | `urllib.request.urlopen(timeout=…)` |
| 重试退避 | `write_chapter`：等 `attempt*5` 秒；`deai`：等 `5 * 2^(attempt-1)` 秒（5/10/20s）；`max_retries` 默认 2（账本/审计/L2 为 3） | 两引擎退避策略**不一致**，是历史遗留 |
| 上下文规模 | 恒定（三件套 + 账本 + 800 字结尾） | 不随章数增长（ADR-2 的核心收益） |

## 七、运维方案

### 7.1 日志在哪

| 位置 | 内容 | 持久化 |
|---|---|---|
| **终端 stderr** | 引擎进度 `[1/4] [2/4] [3/4]`、`[用量] 输入/输出/总 tokens \| finish=`、重试/失败警告 `⚠ …` | ❌ 不落文件，关掉即丢 |
| **Web 服务端 stderr**（`start-web.bat` 的黑窗口） | `  [web] GET/POST …` 访问日志（`log_message` 覆写）、`[web] 缺 story_state.md，自动 init-state…` | ❌ |
| **Web 接口 `log` 字段** | 引擎 stdout+stderr 尾部（`write` 取 2000 字符，`audit/polish/apply` 取 1500 字符） | ❌ 仅本次响应 |
| **前端右下状态条** | 当前动作 + 最近一条日志片段 | ❌ |
| **产物文件** | 体检报告、审计报告、diff JSON、`.bak.md` | ✅ 落盘 |

> **没有日志文件，没有日志轮转**。这是刻意的简化：单机单人工具，出问题直接复现。若要做长期留存，最简单的改造是把 `run_engine()` 的 `out+err` 追加写到 `books/<书名>/engine.log`（需评估：该目录部分入库）。

### 7.2 Key 怎么管

| 环节 | 做法 |
|---|---|
| 存放 | 项目根 `.env`，明文；`.gitignore` 已排除 |
| 读取优先级 | **CLI**：`--key` > 环境变量 `AGNES_API_KEY` > `.env` 的 `AGNES_API_KEY` > 环境变量 `ZHIPU_API_KEY`（历史兼容） |
| | **deai.py**：无 `--key` 参数，只能走环境变量或 `.env` |
| | **Web**：实时读 `.env`（`live_env()`），改完设置**无需重启** |
| 生效链 | 命令行 > `.env` > 内置默认（`DEFAULT_BASE_URL` / `DEFAULT_MODEL`） |
| 备用通道 | `FALLBACK_API_KEY` + `FALLBACK_MODEL` **同时存在**才启用；`FALLBACK_BASE_URL` 缺省沿用主通道 URL |
| 改配置 | 三条路：手改 `.env` / Web ⚙ 设置页（`PUT /api/settings`）/ 命令行参数；Web 只改白名单 6 键，其余行原样保留 |
| 就绪判定 | 服务端 `_check()`：`.env` 中 `AGNES_API_KEY=` 后内容长度 > 10 即认为已配置（**只判长度，不判有效性**）；真正的连通性用 Web「🔌 测试连接」（消耗 4 token） |
| 轮换 | 厂商后台换 key → 改 `.env` 或设置页 → 点「测试连接」验证 |

### 7.3 出问题怎么排查

| 症状 | 先看 | 常见根因 | 处置 |
|---|---|---|---|
| 写章失败、报「模型调用失败（重试 N 次后放弃）」 | 终端 `⚠ 主模型…请求异常` 与 `[用量] finish=` | ① key 无效/欠费 ② base_url 错 ③ 输入过大触发 reasoning 失控（返回空、`finish=length`） | 先点「🔌 测试连接」；再看 `finish_reason`；`finish=length` → 降输入或提高 `reasoning_effort` 抑制 |
| 切了备用还是失败 | 是否有 `⚠ 主模型 … 切换备用模型 …` 这行 | 没打印 → 说明 `FALLBACK_API_KEY` 或 `FALLBACK_MODEL` 有一个没配（代码要求两者都存在） | 补齐两个键 |
| 备用通道报「模型不存在」 | 备用请求体里的 `model` 字段 | 历史 bug：切通道时只换了 URL 没换模型名；现已修（`payload["model"] = ch_model`），并有两条冒烟断言守着 | 跑 `smoke_test.py` 回归 |
| Web 页面能开但按钮点了没反应 / 报 404 `no route` | 服务端 stderr 的 `[web] POST …` | 大概率命中难点 6（POST 路由不可达） | 见 §五 难点 6 修复方案 |
| 页面样式错乱 / 设置面板输入框异常 | 浏览器 Console | 难点 8（模板字符串里的破损 HTML） | 见 §五 难点 8 |
| 章节列表里缺章 / `ch010` 排到前面 | `chapters/` 文件名 | 文件名必须 `ch` + **3 位**数字 + `.md`；不规范名不予识别 | 重命名为 `ch010.md` 格式 |
| 中文乱码（终端 `UnicodeEncodeError`） | 控制台代码页 | Windows 旧控制台 GBK 打不出 `⚠✅` 等字符 | 设 `PYTHONUTF8=1`；或用 `start-web.bat`（已 `chcp 65001`） |
| 端口起不来 `Address already in use` | 谁占了端口 | 上次进程没退干净（实测出现过僵尸进程占着端口） | Windows：`netstat -ano \| findstr :8801` → `taskkill /PID <pid> /F`；macOS/Linux：`lsof -i :8801` → `kill -9` |
| 文件保存失败（Windows `PermissionError` / `EBUSY`） | 是否有别的程序开着该文件 | 编辑器/网盘同步/杀软占用 | 关掉占用程序重试；网盘同步目录建议先暂停同步 |
| 改完代码怕回归 | — | — | `python scripts/smoke_test.py`，23 条断言全绿（零网络、秒级） |
