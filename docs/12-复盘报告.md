## Q1 · 目标达成了吗？

### 1.1 目标 vs 结果

立项要解决的就两件事（README 开篇）：**长篇失忆崩坏** 与 **AI 腔**。

| 目标 | 成功标准（可验证口径） | 实测结果 | 结论 |
|---|---|---|---|
| **治失忆崩坏** | 连写多章后人名/时间线/伏笔/道具不崩 | 示例书《雾城档案》连写 **7 章**（`ch001`–`ch007`），账本能持续追踪「回闪次数 1/3」「薄荷糖储备」「银色鸟形表饰」等跨章事实 | ✅ **达成**（有实物证据） |
| **治 AI 腔** | AI 腔可量化、可改、且改得动 | `ch001–ch005` 均有体检报告；`ch004/ch005` 有 diff JSON 且**已应用过改写**（存在 `.bak.md`）；`ch005` 的两处 hard 级陈词被替换 | ✅ **达成**（有产物证据） |
| **提供审计手段** | 能查出正文与账本的冲突/漏记 | `ch006.一致性审计.md`（4.1 KB）实际查出 4 类问题：计数多算一颗薄荷糖、人名「沈浩/王浩」不一致、账本早于正文确定泥土成分、关键物件「布」漏登记 | ✅ **达成**（报告本身就是证据，抓到了真问题） |
| **零依赖可跑** | 任何装了 Python 的机器能跑 | 全部代码仅用标准库；无 `requirements.txt`；冒烟测试零网络零依赖 | ✅ **达成** |
| **引擎可回归** | 改代码后能快速验证没改坏 | `smoke_test.py` 23 条断言，秒级 | ✅ **达成** |
| **多模型可用** | 换厂商只改配置 | `.env` 三键切换 + 主备 failover；冒烟测试有 5 条断言守 failover | ✅ **达成** |
| **Web 工作台可用** | 三栏工作台建书/写章/审稿 | **部分达成**：文件与 UI 已完整；但 `server.py` 的 POST 路由因缩进不可达（R-13），前端按钮会 404 | ❌ **未达成**（需先修 R-13 + R-14） |

### 1.2 诚实地写：哪些「没有数据」

| 声称 | 缺什么 | 为什么 |
|---|---|---|
| 「写第 50 章和写第 2 章负担一样」 | **无实测数据** | 示例书只写到第 7 章；30–50 章后的账本膨胀（R-03）只是推理，未验证 |
| 「一本书零穿帮」 | **无系统性穿帮统计** | 只有第 6 章做过一次审计，且审计本身有截断漏检（R-10）；其余 6 章没有审计报告，无法声称零穿帮 |
| 「去 AI 腔有效」 | **无前后对照的量化指标** | 有 apply 记录，但没有「apply 前指数 vs apply 后指数」的对照表；且 apply 后是否 re-scan 复查无留痕 |
| 「模型换厂商即用」 | **只验证过 Agnes 一家** | `.env.example` 列了智谱/DeepSeek，但仓库内无这两家的实测记录 |
| 「Web 工作台可用」 | **无端到端验收记录** | 路由缺陷说明它从未被完整跑通过 |
| 「用户（作者）体验好」 | **无第二用户反馈** | 单人项目，无外部用户数据 |

### 1.3 一句话结论

> **两台引擎（连载 + 去味）是真的跑通了，而且产出了能自证的质量证据（7 章正文 + 审计报告 + 改写记录）；Web 工作台是「写完但没验收」，卡在一个缩进错误上。**
> 立项要治的两个病，都拿到了「有效」的实物证据；但所有「规模化」的声称（50 章、零穿帮、多厂商）目前都还只是设计意图，不是实测结论。

### 2.2 变更结构分析

| 分类 | 条数 | 占比 | 说明 |
|---|---|---|---|
| 🔴 故障驱动 / 缺陷修复 | 7 | 39% | 几乎全部与「模型行为不可控」有关 |

**结论**：变更里**近 4 成是故障驱动**，且故障源高度集中——**模型的非确定性行为**（过载、失控、不守边界、输出被截断）。这说明这类项目的主要工作量不在功能，而在「给不可靠的下游兜底」。

## Q3 · 踩了什么坑？

> 前 12 条来自 README 已记录的坑（本轮复核后补充了代码位置与现状）；后 8 条是本轮读码/实测**新核对出来**的。

| # | 坑 | 发生阶段 | 损失 | 下次怎么避 |
|---|---|---|---|---|
| 1 | **推理模型 reasoning 失控吞光 max_tokens**（agnes-2.5-flash 长上下文 + 长创作，返回空、`finish_reason=length`） | 引擎开发早期 | 多次空返回，白等 1–2 分钟 | 所有调用点固定带 `reasoning_effort=low`（`reasoning_effort != "none"` 时才发），`max_tokens` 给足 12000 |
| 2 | **输入超 ~5k tokens 又触发失控**（整章 5500 字塞进账本更新） | ch4 | 账本更新直接失败 | 正文首尾截短（>3200 → 各 1400）；审计再剥掉「## 伏笔账本」整节 |
| 3 | **低版本模型不守边界**（2.0-flash 一次写 1.7 万字、跨多章、称呼串戏） | 模型选型 | 一整章废稿 | 主力锁 `2.5-flash` + reasoning low；称呼规则写死进 `设定.md`；换模型先连写 3 章验证 |
| 4 | **截尾记忆穿帮**（每章 400 字摘要 → 第 2 章编造未发生情节） | 记忆方案 v1 | 方案级返工 | 结构化滚动账本 + 规则 9（冲突必须显式标注，不许悄悄覆盖） |
| 5 | **道具漂移**（徽章从「荆棘眼」漂成「鸟形袖扣」） | 早期写作 | 设定不自洽，需回头改文 | `设定.md` 写死外观 + 账本「关键物件」禁止改外观 + 审计列为第一类检查项 |
| 6 | **Python 字符串里的引号地狱**（中文提示词嵌英文双引号 → SyntaxError） | 提示词编写 | 反复调试 | 提示词里一律用「」或全角引号 |
| 7 | **词表误伤正常表达**（初版把「若有若无」「不是X而是Y」当必腔） | 去味引擎 v1 | 误报、作者不信任工具 | 降为 soft（高频才报）；词表按实战校准，勿凭直觉 |
| 8 | **AI 改 AI 引入新套话**（「某种说不清的金属味」→「若有若无的铁锈气」，后者也在词表） | apply 之后 | 旧腔去、新腔来 | **apply 后强制 re-scan 复查**（已写入流程，但无自动检测） |
| 9 | **文本替换锚吞引号**（对话句以引号开头，切句把引号包进去、改写版没有 → 替换丢引号） | apply 实现 | 正文格式破损 | `SENT_END` 纳入 `"'“”‘’「」『』`；冒烟测试两条断言守住 |
| 10 | **.env 差点入库** | 工程配套 | 潜在安全事故 | `.gitignore` 排除 `.env`/`*.env`，保留 `!*.env.example`；提交前 `git status` 复查 |
| 11 | **Windows 控制台 GBK 打印崩**（`⚠✅` 等非 GBK 字符） | 跨平台 | Windows 用户直接跑不起来 | 设 `PYTHONUTF8=1`；`start-web.bat` 加 `chcp 65001`；进度信息走 stderr |
| 12 | **主/备用通道同厂商会连坐** | failover 设计 | 备用形同虚设 | 备用必须选另一家厂商（已写进 `.env.example` 与设置页提示） |
| 13 | **静态文件 `Content-Type` 变 `application/octet-stream`**（扩展名 key 带前导点，与 `splitext` 结果对不上 → `.js` 被当二进制，浏览器拒绝执行） | Web v1 | 页面白屏、脚本不执行 | `os.path.splitext(...)[1].lstrip(".").lower()`（代码第 235 行有注释明示）；**新增静态资源类型时先 curl 看响应头** |
| 14 | **Python 作用域：内层函数里 `x = x or default` 变局部变量 → `UnboundLocalError`** | Web 开发期 | 运行时崩溃 | 读取外层变量只**读**不赋值；要改就显式传参或 `global`。`[待确认：当前代码中已无此写法，现有 `fb_key = fallback_key or …` 读的是外层函数参数，属历史坑]` |
| 15 | **`from-chat` 建书 `KeyError`** | Web v2 | 建书 500 | 先做完整性校验 `if not all(k in files for k in ("设定","角色卡","大纲"))` 再取值；写文件前再逐个 `if k not in files: raise` |
| 16 | **SSE 流式输出**（后端手写 `event:/data:` 双换行、前端手写 `ReadableStream` 分块解析；中英混排 JSON 按块到达会截断多字节字符） | Web v3 | 初期出现乱码/粘包 | 后端每块 `json.dumps(delta, ensure_ascii=False).encode("utf-8")` + `wfile.flush()`；前端 `TextDecoder` 用 `{stream:true}` 并把最后一段留在 `buf` 里下次拼接 |
| 17 | **端口被僵尸进程占住**（实测过端口被占，`start-web.bat` 的 echo 还把端口写错成 8899 → 按提示查半天查不到） | 日常使用 | 排查耗时 | 关窗口后确认进程真的退出；`netstat -ano \| findstr :<port>` 定位；**提示语里的端口必须与启动参数一致** |
| 18 | **JS 连写错误藏在模板字符串里**（`app.js` 的 `<input<type=`、`</textarea">`、`onclick="…"()`、`$const(...)` 未定义函数） | Web v3 | 设置面板渲染异常、建书向导书名不回填 | `node --check` 只能查 JS 语法，**查不出 HTML 字符串破损**；模板字符串拼 HTML 后必须在浏览器实际点开验证 |
| 19 | **手写路由被缩进吞掉（本轮最严重）**：`server.py` 里 `POST /api/books`、`from-chat`、`write`、`audit`、`scan`、`polish`、`apply` 的代码缩进与 `_chat_stream()` 同级，导致它们落进了 `_chat_stream` 方法体（AST 实测：`handle_api_post` 378–414 行，`_chat_stream` 416–**575** 行） | Web v3 加 SSE 时 | **Web 核心功能全部不可达** | ① 加完函数立刻用 `ast` 复核方法边界；② 路由改动后逐条 `curl` 打一遍；③ 手写路由时每个分支以 `return` 收口，禁止「掉下去」 |
| 20 | **模型输出被截断 → 账本结构损坏（已发生）**：`books/雾城档案/story_state.md` 末行停在 `## 关键事件时间线（最近约 10`，缺第 4–7 节 | 写第 7 章后 | **记忆中枢残缺**，续写会建立在错误前提上 | 写章后**必看账本 7 小节是否齐全**；发现截断立刻人工补或 `--state-only` 重算；`[待确认]` 是否加一个「账本结构校验」步骤到写章流程里自动拦截 |

### 3.1 坑的模式归纳

| 模式 | 条数 | 对应的通用对策 |
|---|---|---|
| **模型非确定性**（失控、不守边界、输出截断、编造） | 1,2,3,4,5,7,8,20 = 8 条 | 把「模型会错」当成默认前提：所有模型输出都要有**结构校验 + 人工闸口** |
| **边界/编码处理**（引号、GBK、UTF-8 分块、Content-Type） | 6,9,11,13,16 = 5 条 | 中文 + 跨平台场景下，**每一个字节边界都写一条断言** |
| **工程习惯**（缩进、作用域、校验缺失、僵尸进程） | 14,15,17,18,19 = 5 条 | 无框架 = 无兜底，必须用工具（AST/curl/node --check）代替框架的静态检查 |
| **安全意识**（key 入库、同厂商连坐） | 10,12 = 2 条 | 写进配置模板与 UI 提示，不靠记忆 |

## Q4 · 哪些做法值得保留？

| # | 做法 | 为什么值得保留 | 怎么固化 |
|---|---|---|---|
| 1 | **把记忆做成「人能读、能改、能 diff」的 Markdown 账本** | 这是整个项目最关键的一步。它让「AI 的记忆」从黑盒变成白盒：作者能直接改、能看穿冲突、能用 git 管理 | 账本 7 小节结构写死进 `STATE_TEMPLATE`，规则写进 `STATE_UPDATER_PROMPT`；任何新项目沿用「结构化账本 + 覆盖式重写」套路 |
| 2 | **上下文配方化（只喂精华，不喂全部）** | 恒定上下文 = 可预测的成本与质量；「上一章结尾 800 字」这种具体到数字的配方，比「适当的上下文」可靠一万倍 | 配方集中在 `build_context()` 一处，改配方只改一个函数 |
| 3 | **两级检测：本地零成本筛 + 模型精判** | 本地层提供可解释、可复现的「指数」；模型层解决语境误判。既省钱又不误伤 | `AI_TONE_BLACKLIST` 的 hard/soft 分级 + `SOFT_THRESHOLD` 阈值，是可以直接复用的模式 |
| 4 | **机器不替作者做文风决定**（只自动改 hard 级 + 应用前备份 + 人工确认） | 这是产品定位（AI 是笔，人是作者），也是质量保障 | 三道闸写进 `05-业务流程.md` §2.3，不许因为「用户嫌麻烦」而松动 |
| 5 | **为每一个踩过的坑写一条断言** | 项目只有 23 条断言，但每一条都对应一个真实事故（吞引号、failover 换模型名…），密度极高 | 新坑进 README「踩过的坑」的同时，必须在 `smoke_test.py` 加一条断言 |
| 6 | **零第三方依赖** | 安装门槛是工具类项目的最大流失点；同时它倒逼出「用标准库就能解决」的简洁设计 | 写进 ADR-1；任何 `pip install` 提案都要先过一遍评估 |
| 7 | **注释里写「为什么」而不是「做了什么」** | 代码里大量注释记录了故障现场（「ch4 实测修复」「防输入 >5k tokens 触发推理失控」「关键：切备用通道时必须把模型名换掉」），后人不用重踩 | 保持这个注释风格：故障修复必须留下「现象 + 原因 + 解法」三要素 |
| 8 | **主备双厂商 failover** | 唯一的下游就是模型 API，单点故障必须兜 | 保持 `FALLBACK_*` 配置与 5 条 failover 断言（其中 2 条专门守「备用请求带备用模型名」） |
| 9 | **提示词用 `replace` 不用 `format`** | 一行代码避开了一整类「正文含花括号导致崩溃」的事故 | 涉及把用户内容填进模板时，一律用 `replace` 或转义 |
| 10 | **先出报告、后改文件**（审计只读、polish 不改正文、apply 才写） | 每一步都可反悔，是「人机共创」在工程上的落点 | 保持「只读 → 报告 → 确认 → 写入」的四段式，新增能力也照此设计 |
| 11 | **把「不做的事」明确写下来** | README 的「不做」清单、`.gitignore` 排除 `chapters/`、设置页只改 6 个白名单键——边界清晰，事故面就小 | 继续维护 `03-范围边界.md`；新增能力时先问「换来的是什么可以下线」 |

### 4.1 不建议保留的做法

| 做法 | 问题 | 建议 |
|---|---|---|
| 手写路由 if 链 | 缩进错一格就整段失效（坑 19），且 docstring 与实现已经脱节 | 至少把路由表抽成声明式结构；或每个分支强制 `return` 收口 |
| 前端用模板字符串拼大段 HTML | 语法检查不到里面的破损（坑 18） | 关键面板改用 `document.createElement` 或模板 `<template>` 标签 |
| 两引擎重试退避不一致（`write_chapter` 线性 5s、`deai` 指数 5/10/20s） | 行为不可预测，排查时容易误判 | 统一退避策略 |
| 只判长度的 Key 就绪检查（`len(...) > 10`） | 填错了也显示 ✅ | 至少加格式前缀校验（如 `sk-`/`lz-`），真正的可用性交给「测试连接」 |
| 产物流在 `chapters/` 又不入库 | 正文零版本控制（R-11） | 至少提供一键导出/归档命令或文档化的备份流程 |

## 五、下一次同类项目的三条行动项

1. **第一天就把「模型会错」写成架构前提**：所有模型输出（正文、账本、JSON）都要有结构校验与人工闸口，本项目最严重的两个问题（账本截断、路由失效）都是「没有校验」的后果。
2. **Web 化之前先跑通 CLI 并留断言**：本项目的引擎质量高、Web 质量低，落差来自「引擎有 23 条断言守着，Web 一条都没有」。
3. **每次「加功能」都问一句「换来什么下线」**：Web v1→v3 是在一天内连加三波的，代价是 `server.py` 与 `app.js` 都留下了未验收的缺陷。
