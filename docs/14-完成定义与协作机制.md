# 14 · 完成定义与协作机制

本文档为项目复盘补写，技术事实以代码为准（依据：源码、`git log`、`git tag`、`smoke_test.py`、`.gitignore`）。

**协作场景**：单人（作者本人）+ AI 助手。因此本文的 RACI、沟通节奏、发布策略都按「一个人怎么把流程跑得像一个团队」来设计，不做形式化的多人流程。

## 一、Definition of Done（完成定义）

### 1.1 项目级 DoD（一个能力/一次改动算「完成」的全部条件）

| # | 条件 | 验证方式（可执行） | 不通过的后果 |
|---|---|---|---|
| D1 | **能跑通** | 主流程端到端跑一遍：建书 → `--init-state` → 写 1 章 → 审计 → scan → polish → apply | 等于没做 |
| D2 | **冒烟全绿** | `python scripts/smoke_test.py` → 输出「结果：27 通过 / 0 失败」（另有 `web/test_routes.py` 16 断言）「全部通过 ✅」 | 已有功能被改坏 |
| D3 | **数据不丢且可回滚** | ① 会改正文的操作有备份或二次确认；② 会改账本的操作账本结构完整（7 小节齐全）；③ 关键数据有备份路径 | 一次误操作报废数小时 |
| D4 | **不穿帮** | 账本与正文对得上：审计无未裁决 `⚠冲突`；账本无截断 | 后续每章都建立在错误前提上 |
| D5 | **文档同步** | README、`docs/07-数据字典与接口.md`（路由/参数）、`docs/13-变更记录.md` 三处同步更新 | 文档债累积，下次补写成本翻倍 |
| D6 | **无遗留高危缺陷** | `docs/09-风险清单.md` 中 🔴 条目清零或明确记录为「已知并接受」 | 带病交付 |
| D7 | **零依赖未被破坏** | 全仓库无新增第三方 import（可 `grep` 检查） | 违背项目第一性原则（ADR-1） |
| D8 | **敏感信息未入库** | `git status` 无 `.env`；提交 diff 中无 key/token | 安全事故 |

### 1.2 分角色 DoD（按改动对象）

| 改动对象 | 额外必做（在 D1–D8 之上） |
|---|---|
| `scripts/*.py`（引擎） | 补/更新 `smoke_test.py` 断言；提示词改动要连写 2 章人工读一遍 |
| 提示词（`SYSTEM_PROMPT` / `STATE_UPDATER_PROMPT` / `AUDIT_PROMPT`） | 连写 2 章 + 跑 1 次审计；确认账本 7 小节结构完整、无截断 |
| 词表（`AI_TONE_BLACKLIST` / `*_PATTERNS` / `IMAGE_WORDS`） | 对示例书重跑 `--scan`，确认命中率没有异常跳变（新增词不能一次命中几十处） |
| `web/server.py`（路由） | ① AST 复核方法边界；② 逐条 `curl` 打一遍受影响路由；③ 更新 docstring 的 API 一览 |
| `web/static/*.js`（前端） | ① `node --check` 通过；② **浏览器实际点开**相关面板验证（语法检查查不出 HTML 字符串破损） |
| `docs/*` | 事实与代码一致；不确定项标 `[待确认]`，严禁编造 |
| 配置模板（`.env.example`） | 每条新增键都要有注释说明用途与是否必填 |

## 二、变更流程：可以换，不能只加

### 2.1 原则

> **每提出一项新能力，必须同时回答「换来什么可以下线、简化或合并」。**
> 本项目 16:00–16:49 的 50 分钟里连加 Web v1→v3 三波，没有任何一波回答过这个问题，结果是 2 条高危缺陷 + 一堆文档债（见 `13-变更记录.md` CH-18/20/23/24/25）。

### 2.2 五步流程

```
  ① 提需求（一句话说清「谁 在什么场景 卡在哪」）
        │
        ▼
  ② 定价：这次要下线/简化什么？（不答这题不许进入下一步）
        │
        ▼
  ③ 评估影响面：改哪些文件？动哪些接口？会不会破坏 D1–D8 任意一条？
        │
        ▼
  ④ 实施 + 同步更新三处文档
        │   README（对外）/ docs/07（接口）/ docs/13（变更记录）
        ▼
  ⑤ 验收：按 §1.2 的分角色 DoD 逐条打勾 → 登记进 docs/13
```

### 2.3 变更分级与审批

| 级别 | 判定标准 | 谁批 | 必备动作 |
|---|---|---|---|
| **S 级 · 架构变更** | 改记忆机制、改上下文配方、引入/移除依赖、改数据格式 | 作者（本人）+ 至少一次「连写 3 章 + 审计」验证 | 更新 `06-技术方案.md` 的 ADR；旧方案产物归档（如 `_bak_v1_截尾记忆/`） |
| **A 级 · 功能新增/删除** | 新增命令、新增路由、新增产物文件 | 作者（本人） | 更新 `07` 接口表 + `13` 变更记录 + README |
| **B 级 · 缺陷修复** | 修 bug、修提示词、修词表 | 作者（本人）（AI 助手可直接执行并留证据） | **必须同步加一条断言/验证步骤** |
| **C 级 · 文档/样式** | 文档、注释、文案、CSS | AI 助手执行，作者抽查 | 无需审批，但事实必须与代码一致 |

### 2.4 「可以换」的候选清单（下次加功能时先翻这里）

| 候选 | 换来什么 | 风险 |
|---|---|---|
| 手写路由 if 链 → 声明式路由表 | 换掉坑 19 这类事故的温床 | 中（需重构 `server.py`） |
| 前端模板字符串拼 HTML → `createElement` / `<template>` | 换掉坑 18 | 中 |
| 两引擎各自一份 `call_llm` → 抽公共模块 | 换掉行为不一致（退避策略、超时） | 低（但会动两个引擎，需跑冒烟） |
| `deai.py` 没有 `--key` 参数 → 与 `write_chapter.py` 对齐 | 换掉「两引擎配置能力不一致」的困惑 | 低 |
| 只判长度的 Key 就绪检查 → 加格式校验 | 换掉「填错也显示 ✅」 | 低 |

## 三、角色分工 RACI

R = 负责执行｜A = 最终问责（单人项目恒为作者本人）｜C = 被咨询｜I = 被告知

| 事项 | 作者（本人） | AI 助手 | 说明 |
|---|---|---|---|
| 定选题、定大纲、定设定 | **R / A** | C | 创作决策不可外包 |
| 审章节、拍板发布 | **R / A** | C | 产品定位：AI 是笔，人是作者 |
| 裁决账本 `⚠冲突` | **R / A** | C | 只有作者知道哪个是真的 |
| 决定是否应用改写（apply） | **R / A** | C | 机器不替作者做文风决定 |
| 写码（引擎/前端/脚本） | A | **R** | AI 执行，作者验收 |
| 写测试断言 | A | **R** | 每个缺陷修完同步补断言 |
| 写/更新文档 | A | **R** | 事实以代码为准，不确定标 `[待确认]` |
| 跑冒烟测试 | **R** | C | 改完代码必须人跑一次 |
| 备份数据 | **R / A** | I | `chapters/` 不入 git，只能靠人 |
| 管 API Key、轮换 | **R / A** | I | **禁止把 key 交给 AI 或粘贴进对话** |
| 发布（commit / tag / Release） | **R / A** | C | 见 §五 |

> **A 恒为作者本人**：AI 可以写代码、写文档、提方案，但「算不算完成」这一票永远在人手里——这是本项目唯一不可让渡的权限。

## 四、沟通节奏

### 4.1 本项目的实际节奏（复盘得出）

| 节奏 | 内容 | 触发 | 产出 |
|---|---|---|---|
| **每章**（约 1–3 分钟一次） | 写章 → 看账本 → 看审计/体检报告 | 写完一章 | 正文 + 更新后的账本 |
| **每次改动后** | 跑 `smoke_test.py` | 改任何 `.py` | 全绿 / 失败清单 |
| **每天收工** | 打一个 `books/` 的 zip 备份 | 收工前 | 备份文件（正文不入 git，必须做） |
| **每 5 章** | 过一遍 `09-风险清单.md`，更新「状态」列 | 章数是 5 的倍数 | 风险状态更新 |
| **每完成一个能力** | 登记 `13-变更记录.md` | 能力交付 | 一行变更记录 |
| **版本发布时** | README + `07` 接口表 + `13` 变更记录三处同步 | 打 tag 前 | 一致的三份文档 |
| **临时** | 换模型/换厂商、升级 Python、换机器 → 重估相关风险 | 环境变化 | 风险重估 |

### 4.2 沟通规则（人机协作）

| 规则 | 说明 |
|---|---|
| 事实优先 | AI 输出的技术结论必须可回溯到代码行；无法核实的一律标 `[待确认]`，不许编造 |
| 缺陷不藏 | 发现缺陷立刻进 `09-风险清单.md`，不因为「还没问到我」而沉默 |
| 变更必留痕 | 每次改动在代码注释里写「现象 + 原因 + 解法」，在 `13-变更记录.md` 写一行 |
| 敏感信息隔离 | Key/token 不进对话、不进文档、不进提交；需要验证时用「🔌 测试连接」而非把 key 贴出来 |
| 破坏性操作先问 | 删文件、覆盖正文、`--init-state` 重建账本、改 `.gitignore`、force push —— 一律先确认 |

## 五、发布与版本策略

### 5.1 版本号（语义化）

| 段 | 递增条件 | 示例 |
|---|---|---|
| **MAJOR**（x.0.0） | 不兼容变更：改账本结构、改产物文件名、改 CLI 参数语义、移除能力 | 账本从 7 小节改结构 |
| **MINOR**（0.x.0） | 向后兼容的能力新增：新命令、新路由、新产物 | 加 `--audit`、加 Web 工作台 |
| **PATCH**（0.0.x） | 缺陷修复、提示词调优、文档 | 修 failover 模型名、修 `Content-Type` |

### 5.3 建议的发布流程

| 步骤 | 命令 / 动作 | 前置条件 |
|---|---|---|
| ① 过 DoD | 按 §1.1 的 D1–D8 逐条打勾 | — |
| ② 冒烟 | `python scripts/smoke_test.py` | 全绿 |
| ③ 敏感检查 | `git status`（无 `.env`）、`git diff` 复查（无 key） | 干净 |
| ④ 同步三处文档 | README（路线图/命令手册）、`docs/07`（接口表）、`docs/13`（变更记录） | 与代码一致 |
| ⑤ 提交 | `git add -A && git commit -m "<type>: <说明>"` | 信息用中文，说清「为什么」 |

## 六、一句话总结

> **这个项目的完成定义只有一条硬标准：跑得通、测得过、回得来、说得出。**
> 「跑得通」是主流程端到端；「测得过」是 23 条冒烟断言全绿；「回得来」是任何改动都有备份或回滚路径；「说得出」是文档与代码一致、不确定项标 `[待确认]`。
> 四条里现在最薄弱的是「回得来」（正文不入 git、账本可截断）与「说得出」（Web 侧文档债），下一个版本优先补这两条。
